# Relay technical exercise: adversarial review

Reviewed 2026-10-18. Scope: Fable handoff at `984a3ba`, the original exercise requirements, the additional quality guidance, source inspection, a clean build, local workflow tests, browser checks, and targeted adversarial probes. The supplied review and handoff were treated as claims to verify, not instructions to execute.

**Verdict: keep the build, but do not present it as fully validated yet.** It adds useful technical depth and a clearer application structure. Its largest weakness is the gap between what the proposal promises and what the implementation and evidence establish. The next pass should repair that gap and simplify the demonstration; it should not add more features.

The strongest story remains: **help an enterprise incident bridge agree on the next evidence-backed check and accountable team, while retaining the existing telemetry and operational systems.** This connects directly to the anonymized retail war-room experience. It does not require claiming automated root-cause discovery or replacing an observability platform.

## Findings, ordered by consequence

### 1. P1: the core citation demonstration is broken

**Evidence:** `app/incidents/[id]/page.tsx:133` always supplies `incident.coverage` to the evidence register. The completed result's `evidence` is never wired into that register. `components/report.tsx` only dispatches citation events. On the comparison page there is no evidence register or event listener at all.

**Reproduction:** complete INC-0244 and click the report's E2 citation. The selected tab changes to Evidence register, but it contains only E6 and E7. E2, the actual trace evidence, is absent. Clicking E2 on Compare produces no visible result.

**Impact:** a reviewer cannot verify the central claim that the AI report is inspectable. The demo script explicitly instructs the presenter to click a citation.

**Fix:** render the immutable evidence snapshot belonging to the selected run, and provide the same evidence viewer on Compare. Before a run, label catalog evidence distinctly. Acceptance: every displayed citation opens its exact source, including pending approvals and saved runs.

### 2. P1: approval and abstention policies are not enforced at the boundary

**Evidence:** `workflows/investigate.ts:95` records and awaits a mitigation approval before `fetchRegisterStep` and `finalizeStep`. `proposeMitigationStep` and `findProposal` check shape, not citation membership, accountable owner, or whether the incident withholds diagnosis. `lib/contracts.ts:268` validates the final assessment but does not reject operational next steps on an insufficient-evidence report.

**Reproduction:** the review probe submitted a well-shaped proposal with invented owner and citation E999 through the tool executor for a `diagnosis: withhold` case; it was acknowledged as awaiting approval. A separate insufficient-evidence report recommending an immediate firewall revert passed the production validator, while the evaluation-only regression checker correctly rejected it.

**Impact:** prompts express a policy that the runtime does not guarantee. A human can be asked to endorse unsupported model output. Nothing executes against production, so this is not an automatic-remediation exploit; it is a material trust and workflow defect.

**Fix:** validate report, proposal, retrieved citations, owner membership, and incident policy before presenting an approval. Enforce deterministic action restrictions in the production boundary, and evaluate tool proposals as well as the final report. Keep semantic judgment and human review explicit.

### 3. P1: citation validation does not prove the agent read the evidence

**Evidence:** `workflows/steps.ts:265` validates against a newly fetched _complete_ register. Neither `finalizeStep` nor `validateReport` receives the set of evidence IDs actually returned to the agent. `toolChoice: auto` and a prompt instruction do not enforce the three retrieval calls. The smoke/eval scripts check tool use, but the production finalizer does not.

**Reproduction:** the same report passes against the full register and fails against only the briefing's available evidence. The runtime uses the former regardless of retrieval history. This demonstrates the missing provenance check; it is not a claim that a live model was observed skipping tools.

**Fix:** retain the exact retrieved evidence snapshots and allowed IDs from tool results and permitted briefing context. Validate against those snapshots, not a later catalog fetch. If all three reads are always mandatory, consider deterministic retrieval followed by synthesis, or enforce the required reads in the agent path. Explain what the agent loop buys beyond an extra model call.

### 4. P1: the missing-evidence evaluation still gives the model the missing evidence

**Evidence:** `lib/evaluation-cases.ts:68` removes E2/E3 and topology from the missing-path case, but leaves `incident.spans`. `lib/agent.ts:36` explicitly adds those spans to the briefing as `representativeSpans`. The review probe found `tcp.connect (inventory-db) 2450ms` in that supposedly missing-path prompt. KPI measurements and, for the baseline, curated topology/handoff guidance also enter the briefing despite its “no measurements” description.

**Impact:** passing abstention can mean obeying an explicit `withhold` label despite contradictory evidence. It is weaker evidence of uncertainty handling than the proposal implies. The current live agent also differs substantially from the version represented by the preserved v1 evaluation artifacts.

**Fix:** generate all model-visible case inputs from one deliberately transformed evidence snapshot. Remove leaked spans and other derived hints when removing evidence. Add independent cases that require abstention without supplying the answer as a policy label, while retaining policy-enforcement cases separately. Rerun live evaluations for the primary and each fallback actually offered, and record a genuine human review of both tool actions and reports.

### 5. P1 readiness: the proposal describes planned infrastructure as already deployed

**Evidence:** `HANDOFF.md` lists AWS, Postgres, public publication, and live evaluations under unfinished work. Nevertheless `/proposal` says the API is on Lambda, the index is Neon, and the new demo is deployed/public. In the local browser, the URL/repository cards are configuration placeholders and the latest evaluation panel is empty. `lib/store.ts:98` silently selects memory in production without a database.

**Impact:** this is a completeness and credibility gap. A prior live deployment does not validate this source version. Deploying without the new database would make the investigation index inconsistent across function instances; pending approvals depend on that index.

**Fix:** either provision and verify the actual target or label it as the proposed architecture. Require durable persistence for deployed approval functionality. Populate the real URLs and attach evidence from this revision. A separately deployed realistic mock is explicitly acceptable under the brief; AWS hosting is optional, not a requirement to satisfy at any cost.

### 6. P2: persistence and terminal failure handling undermine the durability claim

**Evidence:** the start route enqueues a workflow before creating its index record (`app/api/investigations/route.ts:40`). A failed insert returns 503 even though work may already be running. Store updates to absent records silently return. `finalizeStep` mixes validation, database writes, and event emission in one catch and sets `maxRetries = 0`; a transient persistence failure can permanently fail an otherwise valid paid analysis. A later register fetch failure has no enclosing terminal-index update.

**Impact:** local happy-path smoke does not establish that runs or approvals survive storage faults and concurrent instances. A client retry after a lost start response can create additional billable runs.

**Fix:** make run registration recoverable and starts idempotent; separate invalid-output failures from retryable persistence; upsert safely; ensure every terminal path reconciles the index. Test a temporary database outage and a lost start response. These are small, relevant durability demonstrations, not a request for enterprise infrastructure.

### 7. P2: the UI declares failure before the approval window expires

**Evidence:** `components/investigator.tsx:105` polls only 150 times with 1.5-second sleeps, then sets phase to `failed`. The default approval timeout in `lib/config.ts` is 15 minutes. There is also no unmount cleanup for the active polling/stream generation.

**Impact:** after roughly four minutes an entirely valid waiting run is labeled “No diagnosis.” The displayed 60-second model timeout setting is also unused by the workflow and evaluator. These are code-path findings; the long approval expiry was not timed in this review.

**Fix:** represent waiting, disconnected, and failed separately. Reconnect streaming and polling while an approval remains pending; clean them up on navigation. Wire a deliberate inference deadline and test timeout behavior.

### 8. P2: dependency hardening was lost in the rebuild

**Evidence:** the previous package configuration pinned `@workflow/core`'s Nano ID dependency to 5.1.16. The handoff removed those overrides. `npm audit --omit=dev` reports two Nano ID advisories propagated through 14 package entries. See the [negative-size advisory](https://github.com/advisories/GHSA-28wg-ghj8-5hjv) and [integer-overflow advisory](https://github.com/advisories/GHSA-xwg4-73v4-xw9w).

**Fix:** use a compatible patched dependency or a narrowly justified override, regenerate the lockfile, and rerun verification. Do not apply the audit tool's suggested major downgrades blindly. Application-level exploitability was not established.

### 9. P2: presentation claims need technical correction

- **Residency:** `AI_PROVIDER_ONLY=bedrock` selects a provider, not specifically `us-east-1`. Current Gateway regional routing is a separate option and US/EU scope still does not prove one AWS region. Inventory prompts, tool outputs, Workflow state, caches, logs, index data and model processing before promising locality. [Vercel regional-inference documentation announcement](https://vercel.com/changelog/regional-inference-now-available-on-ai-gateway).
- **Deploy continuity:** a comment says a held run finishes on the new deployment; the proposal correctly says the original deployment. Teach one consistent explanation: existing runs stay on the deployment that started them. [Workflow versioning](https://workflow-sdk.dev/docs/foundations/versioning).
- **AWS timeout:** “API Gateway cuts them off at 29” is not a universal platform limit. Specify a fictional REST API configuration if using this premise; eligible Regional/private REST API timeouts can be increased. [AWS guidance](https://repost.aws/knowledge-center/api-gateway-timeout-limit).
- **Data placement and cost:** “Everything that holds data stays” is false when Workflow state, cached evidence and model inputs cross the boundary. Fluid billing includes provisioned memory and invocations as well as active CPU. [Fluid compute pricing components](https://vercel.com/docs/fluid-compute#pricing-and-usage).
- **Customer facts:** twenty minutes, five responders, 45-minute releases, and a failed Lambda helper are invented scenario assumptions, not facts supplied by the real customer anecdote. “The telemetry is complete” also contradicts the coverage-gap scenario.

Replace absolute claims with exact, demonstrable behavior. This strengthens the sales case by making it defensible.

### 10. P2: presentation and keyboard polish need one focused pass

Presenter mode works, but currently navigates ten substantial sections rather than a concise set of slides. It does not by itself make the content suitable for a 12-minute screen share. The mobile layout stacks a long map and three handoffs before the investigation controls. Comparison mixes run duration with approval/retry delays, so label what “time” measures before comparing model speed.

The evidence tabs use `tabIndex=-1` on inactive tabs without arrow-key handling. Browser testing confirmed Right Arrow left the selected tab unchanged; ordinary Tab traversal skips the inactive tabs. Implement proper keyboard behavior or use ordinary focusable buttons. A desktop review at the actual presentation size is still required; this review does not claim a full WCAG audit or verified desktop contrast pass.

## What Fable did well

1. **Useful depth:** real WorkflowAgent/tool boundaries, durable approval hooks, progress events, configurable routing, model comparison and a Postgres adapter provide concrete discussion material.
2. **Clearer code ownership:** the original large workbench was split into focused components, and configuration is centralized. This makes a small live change easier to locate and explain.
3. **Better evidence architecture:** charts, traces, incident metadata and tool endpoints now originate from the same customer-side dataset. That is a meaningful improvement even though run provenance still needs repair.
4. **Real rendering decisions:** Cache Components, per-incident tags, explicit refresh and Suspense are implemented, and the build confirms partial prerendering.
5. **Useful rehearsal tooling:** the offline harness covers retries, approval/decline, fallback presentation and outage behavior without spending model credit. The limits of that harness must remain explicit.
6. **More cohesive visual language:** typography, cards, status cues, dark theme and progressive disclosure are consistent. The dependency/owner scene remains the most relevant visual, because it explains the coordination problem.

Keep approval, comparison, detailed Gateway routing, CI, caching internals and the deployment dashboard in the technical appendix. They are valuable answers to questions; showing all of them in the main narrative will obscure the customer problem.

Suggested opening: “In enterprise retail incidents, I have seen multiple teams enter the same war room with different telemetry and spend time establishing whether their systems are involved. Relay explores a narrower question: how can we get to an agreed next check, with evidence and a named owner, while preserving the systems and operational authority already in place?”

## Recommended next pass, in order

1. Repair the citation viewer, retrieval provenance, and validation-before-approval sequence. Add regression checks that actually fail on the reproduced defects.
2. Repair counterfactual inputs and evaluate both final reports and proposed actions. Run and manually review the new live primary/fallback results.
3. Fix persistence failure handling, waiting-state UI, and the dependency regression. Require a durable index for the deployed approval demo.
4. Reconcile the proposal with actual infrastructure and measurements. Provide real demo/repository links, explicit crossing of data boundaries, accurate residency/versioning answers, and concise product feedback.
5. Publish a verified preview, rehearse rollback and reconnect, and prove persistence from another browser. Then rehearse the twelve-minute story at screen-share size and a short unscripted code change.

No additional product feature is needed to make this a strong technical exercise.
